# Technical Decisions & Trade-offs

| Decision | Alternative considered | Why this way |
|---|---|---|
| `EventCategory` derived from the real `msgType` field | A fabricated `device_type` column (the original assumption, before the real CSV arrived) | The real data has no such column; `msgType` is the only always-present categorical field and maps directly onto the case brief's own four event kinds |
| 4 topics, grouping `msgType`'s 11 raw values | One topic per raw `msgType` | 11 topics for very uneven volumes (1 row up to 45 rows) fragments operations for no benefit at this scale |
| One topic per event category | A single `device.events` topic, routed by a header or field | Per-category topics let partition count, retention, and consumer concurrency be sized per category (`PROPERTY_CHANGE` is ~45% of the sample, `OTHER` ~10%) and isolate a failing category's retries and DLT from the others; the cost is four topics and four listeners to operate instead of one |
| Blocking retries in place (`DefaultErrorHandler`, 3 retries at 1s/2s/4s, then `<topic>.DLT`) | Non-blocking retry topics (`@RetryableTopic`) | Retrying in place keeps per-device ordering intact, since nothing behind a failing record on its partition is consumed until it succeeds or is dead-lettered. The cost is that a failing record stalls its whole partition for up to ~7s; retry topics would keep the partition flowing but let a device's later events overtake the one being retried |
| At-least-once delivery + idempotent consumer (offsets committed by the listener container only after the record is handled) | Kafka transactions / exactly-once semantics | The side effect is a Postgres write, outside Kafka's transaction boundary, so Kafka EOS alone wouldn't make it exactly-once anyway. Redelivery after a crash or rebalance is made harmless by the `eventId` dedup check plus the unique constraint, which is simpler and cheaper than distributed transactions |
| `timestamp_log` as the single timestamp source, parsed via `OffsetDateTime` | The nested `utcTime`/`time` fields inside `body_completo` | Those vary format (epoch seconds vs. compact strings) by message family; `timestamp_log` is uniform across all 100 rows |
| Native id (`body_completo.id`/`alarmId`) preferred over hash, when present | Always hash | Real native ids exist for 26/100 rows, verified unique; more faithful to the source system |
| Blank `did` → fallback to `body_completo.deviceId` → `"UNKNOWN"` | Reject the row at ingestion | Demonstrates RT04 tolerance on real, mildly inconsistent data instead of dropping 2 real rows |
| DLQ demo via 4 appended synthetic rows, clearly labeled | Force a failure into a real row; cover DLQ only in the integration test | The case explicitly allows adding events beyond the original 100; a labeled synthetic row keeps the real dataset unmodified and still demonstrates retry/DLQ live via `docker compose` |
| Two independent domains (`device`, `audit`) | One domain covering ingestion+processing+audit | Audit is one of potentially several independent consumers of the event stream (e.g. a future `notification` domain) |
| Ports as Java interfaces, standard Spring autowiring | Abstract classes; manual composition root | Idiomatic Java/Spring; same dependency-inversion guarantee |
| Duplicates/failures: log only, no audit row, no `status` field | Persist `DUPLICATE`/`FAILED` rows | The audit table should only ever reflect successfully processed events |
| PostgreSQL for the audit store | H2 | Real persistence across restarts; works with Testcontainers and the Docker Compose bonus |
| Spring Boot 3 + spring-kafka | Plain kafka-clients, or a different framework (Quarkus, Micronaut) | spring-kafka provides the listener containers, concurrency, error handler, and DLT recoverer this design relies on, so they're configuration rather than hand-written poll loops; Actuator + Micrometer give health and Prometheus metrics for free. The cost is a heavier runtime and slower startup than a hand-rolled consumer |
| Flyway migrations, Hibernate in `validate` mode | Hibernate `ddl-auto: update` | The schema (including the `event_id` unique constraint the idempotency strategy depends on) is versioned and reviewable SQL, never inferred from entity classes; the app refuses to start against a schema that doesn't match |
| Docker Compose for the whole local stack (Kafka KRaft, Postgres, app, Prometheus, Grafana) | Documenting manual installation of each component | One command reproduces the full environment for evaluators, with healthchecks gating startup order; it is a local/demo topology only, not a production deployment |
| Testcontainers (real Kafka + Postgres) for integration tests | Embedded Kafka (`@EmbeddedKafka`) + H2 | Tests run against the same Kafka and Postgres images used in `docker-compose.yml`, so they exercise real broker delivery, real DLT publishing, and the real Postgres unique constraint. The cost is that the suite needs Docker and takes longer |
| One structured `ExecutionLog` per behaviour | Scattered `logger.info` calls | Every behaviour's outcome is a single, greppable, structured line |
| Random event stream: unbounded publish rate, no producer-side backpressure | A rate-capped generator | The tool's whole point is making the consumer's real ceiling visible; a self-imposed producer cap would just move the bottleneck and hide what we're trying to demonstrate |
| Random event stream: a single dispatch slot's publish failure is swallowed (not rethrown), the stream itself never stops | Stop the stream on the first publish failure | One flaky slot must never kill an otherwise-healthy demo; the publisher adapter still logs each failure individually, but nothing aggregates them, so the trade-off is that spotting a *sustained* problem needs the `requested − published` metric ratio (now the `RandomStreamPublishGap` alert) rather than one obvious log line |
| Random event stream: in-memory state only, cleared on restart | Persist stream config/state across restarts | It is a load-generation/demo tool, not a production feature — losing a running stream on app restart is an acceptable, explicit trade-off (see `docs/superpowers/specs/2026-10-11-random-event-stream-design.md` §2) |

## Known limitations

- No authentication/authorization on the REST endpoints — out of scope for the case.
- DLT replay is manual, by design.
- A frontend for browsing `/audits` is a planned separate project, not part of this submission.
